# board-power-t5s3-v2

## Identity and package

`board-power-t5s3-v2` is the reusable BQ25896-backed USB VBUS source provider currently published for the T5S3 driver set. The migrated package version is **0.1.5**, driver ABI **2**, architecture **xtensa-esp32s3**, and executable `driver.elf`. The driver provides `board.power.vbus@1` and requires exactly `i2c.bus@1`, `platform.clock@1`, and `board.power.bq25896.profile@1`.

The source manifest is marked `experimental-unpublished`, while the upstream release index publishes tag `driver-board-power-t5s3-v2-v0.1.5`. The canonical ELF is **10,860 bytes**, SHA-256 `1f6e43bf15610b6ce2e30131c830d9d1b2643ec114471d216f90322fbdde3834`.

## Exported root

The sole public root is:

`const risc_driver_v2 *t5_driver_get(uint32_t abi)`

It returns the static driver object only for `RISC_PROVIDER_DRIVER_ABI_V2`. The root identifies driver `board-power-t5s3-v2`, capability `board.power.vbus`, capability API `RISC_USB_VBUS_API_V1`, and the `start`, `stop`, and driver-level `quiesce` lifecycle callbacks.

The capability object is the additive `risc_usb_vbus_monitor_api_v1` extension. Its base `risc_usb_vbus_api_v1` exposes `acquire_host`, `release_host`, and `quiesce`; the monitor adds `input_status` and sets `RISC_USB_POWER_IDLE_PROBE_REQUIRED`.

## Required profile and electrical constraints

The provider does not hard-code T5S3 electrical policy. It copies one admitted `risc_bq25896_profile_api_v1` dependency before claiming hardware. The profile is rejected unless:

- API version is 1 and the structure is large enough;
- `max_host_milliamps` is nonzero and does not exceed the configured boost-current limit;
- boost voltage is an exact BQ25896 step between 4550 mV and 5510 mV, inclusive, using 64 mV increments;
- boost-current limit is one of 500, 750, 1200, 1400, 1650, 1875, or 2150 mA;
- boost settle time is 1 through 500 ms;
- input settle time is 220 through 5000 ms;
- transient recovery window is at most 500 ms;
- if transient recovery is enabled, its stable interval is 200 through 500 ms; if disabled, the stable interval must be zero.

The separately migrated `t5s3-usb-power-profile` provider supplies the current T5S3 values used by the upstream fixture: 500 mA consumer admission, 5126 mV boost, 1200 mA boost limit, 80 ms initial boost settle, 500 ms input settle, 250 ms transient window, and 200 ms clean-stable interval. Those values belong to that profile provider, not to the reusable BQ25896 implementation.

## Hardware access and matching

The BQ25896 device address is fixed at **0x6B**. All register I/O goes through the admitted `i2c.bus@1` provider. Each transaction uses a **100 ms** bus timeout. The driver claims address 0x6B once during `start` and retains that device claim until provider quiescence.

After claiming the address, the implementation reads register `0x14` and accepts only a part-number field whose bits `0x38` are zero, which the source identifies as BQ25896. An ACK at 0x6B alone is explicitly not accepted as device identity. It also reads the power-control register before reporting successful start.

Relevant register interactions present in the source include ADC control `0x02`, power control `0x03`, boost configuration `0x0A`, status `0x0B`, fault `0x0C`, battery ADC `0x0E`, VBUS ADC `0x11`, and identification `0x14`.

## Start and dependency admission

`start` requires exactly three dependencies and rejects duplicates, missing capabilities, unknown capabilities, wrong API versions, or incompatible structure sizes. Required callbacks are:

- I2C: `claim_device`, `transact`, and `release_device`;
- clock: `monotonic_ms` and `sleep_ms`;
- immutable BQ25896 profile data satisfying the validation above.

A failed chip probe occurs after the I2C claim. The provider remains responsible for that claim until `quiesce` releases it; the loader must not assume a failed `start` means no resource was acquired.

## Host-source acquisition

`acquire_host` rejects a null output token, inactive/unclaimed/faulted state, an existing source lease, zero current, requested current above the profile maximum, an exhausted token sequence, or an unavailable monotonic clock. False results zero the caller's lease output.

Before any source write, the provider performs a read-only preflight. It rejects existing external-input/status evidence, existing OTG source state, unreadable status, or a live boost fault. BQ25896 fault register `0x0C` is read twice in separate transactions: the first read observes latched history and the second observes current fault state. A historical cleared boost fault is logged but does not by itself block a new source attempt.

The driver snapshots the current power, boost, and ADC-control registers before modification. It then configures the profile's boost voltage/current limit, enables continuous ADC conversion while preserving unrelated ADC-control bits, disables charge, and requests OTG. A lease token is created before writes so a write that may have partially applied still pins provider ownership.

The source waits the profile-defined initial settle interval and then verifies source state. Startup verification is bounded by **1500 ms** and 10 ms sample intervals. Success requires OTG still enabled, VBUS status reporting OTG, no live boost fault, and a VBUS ADC code of at least 18, which the source documents as at least 4.4 V.

When the profile enables transient recovery, at most one cleared, latched startup boost fault is tolerated inside the configured transient window. The driver then requires an uninterrupted clean period of the profile's stable duration and a fresh adequate ADC result. A repeated transient, a live fault, loss of OTG regulation, or timeout fails the acquisition.

## Rollback, release, and quiescence

A failed acquisition attempts to restore the saved power, boost, and ADC state. Source-off verification is independently bounded by **400 ms** and 10 ms samples. The provider verifies OTG is cleared and status no longer reports OTG before restoring other settings, then reads back power, boost, and ADC configuration.

If rollback cannot prove a safe restored state, the provider sets a faulted state and retains its lease/resource ownership rather than presenting a false clean shutdown. A later explicit release may retry recovery.

`release_host` accepts only the active lease and likewise requires successful disable-and-restore verification. On failure it keeps the provider faulted and retains ownership. On success it clears the source lease and begins a new input-observation settling interval.

Provider `quiesce` returns false while a source lease or source request remains. Once sourcing is clear, it releases the I2C device claim. If the I2C release fails, quiescence fails and the provider remains pinned. `stop` only clears dependency pointers and started state after leases, source state, device claim, and fault state are all clear.

The implementation uses static state and contains no internal mutex or atomic synchronization. Its source comment states calls must be serialized by the generic provider executor; independent concurrent-call safety is therefore not claimed here.

## Input-power monitoring

`input_status` returns `RISC_USB_POWER_UNKNOWN` when the provider is inactive, faulted, an I2C read fails, or the clock is invalid. It never treats an unowned OTG state as incoming external power.

When the provider owns an active source lease, it reports `RISC_USB_POWER_SOURCE`. After source-off, it reports `RISC_USB_POWER_SETTLING` until the profile's input-settle interval has elapsed. After settling, status/ADC evidence of VBUS input returns `RISC_USB_POWER_EXTERNAL`; otherwise it returns `RISC_USB_POWER_ABSENT`.

The capability sets `RISC_USB_POWER_IDLE_PROBE_REQUIRED`, matching the ABI comment that this board/provider requires source-off observation to distinguish incoming power reliably.

## Failure behavior

The implementation fails closed on dependency/profile mismatch, chip mismatch, I2C errors, clock failure or rollback, external-power conflict, live or repeated boost fault, source timeout, readback mismatch, invalid lease token, or failed device-claim release. Unknown or uncertain hardware state is reported as unknown rather than interpreted as permission to source VBUS.

No alternate PMIC, alternate BQ25896 address, additional board rail switch, charger-policy service, or concurrency guarantee is established by this source. The profile header explicitly states that boards requiring extra rail or OTG-pin switching need a composed provider; this profile interface does not claim such wiring support.

## Tests and validation

The exact upstream fixture `test/drivers/board_power_t5s3_v2_test.c` uses the T5S3 profile plus simulated I2C and clock providers. It verifies dependency-count rejection, source/input distinction, settling behavior, repeated park/reacquire without dropping the I2C claim, current-limit admission, 5.126 V / 1.2 A T5S3 boost configuration, rollback after write failures, retry after release failure, source timeout, delayed ADC qualification, historical versus live boost faults, one qualified transient recovery, rejection of a second transient, invalid clock behavior, malformed profile rejection before I2C claim, and rejection of another chip at address 0x6B.

The fixture success string is:

`BQ25896 reuse/profile validation plus T5S3 VBUS: v1.2.16 1.2A boost, qualified transient recovery, repeat/live faults, ADC, conflicts, rollback, timeout, retry: PASS`

Canonical ELF parity is not claimed until the standalone Xtensa builder reproduces the 10,860-byte published artifact.

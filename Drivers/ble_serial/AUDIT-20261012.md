# BLE serial 0.1.1 readiness audit

Baseline: Drivers `8ec572af94ee6e844b1685d8d050471cd58cad87`.
No hardware, RF link, vehicle, or physical display timing was exercised.

## Verified defect and correction

`make_channels` stored the RX notification choice in bit `0x80` of the TX
characteristic-properties byte. Bluetooth defines that same bit as Extended
Properties. If TX advertised Extended Properties and RX supported indications
only, the provider wrote `01 00` to the RX Client Characteristic Configuration
Descriptor. The correct indication enablement is `02 00`.

A conforming peripheral can refuse this request, resulting in FAULT with the
misleading message `Subscription refused; pairing may be required`. A peripheral
that accepts the unsupported notification bit may instead never deliver data.

Version 0.1.1 stores the RX choice in a separate Boolean. TX write properties,
public ABI, unpaired-only policy, selected peer/channel, and HCI ownership do not
change. The regression augments the real NimBLE HCI/ATT fixture with an
extended-properties transmitter and an indication-only receiver. The independent
ATT server accepts only `02 00` and verifies the provider reaches READY.

## Reproduction

Build and run the unchanged baseline's host driver, then pass that `driver.so`
to the new regression:

```
python test/ble_serial_extended_indication_test.py /path/to/baseline/driver.so
```

Expected failure on the baseline: `CCC write: 0100 expected: 0200; state: 10`.
The test raises `TX extended-properties bit incorrectly selects notifications
for indication-only RX`.

Run the corrected version:

```
python scripts/test_ble_serial.py
python scripts/test_ble_serial.py --sanitize
NATIVE_DRIVER_CC=/path/to/xtensa-esp32s3-elf-gcc python scripts/build_ble_serial.py
```

All 11 real-stack cases passed normally and under ASan/UBSan. The new case prints
`CCC write: 0200 expected: 0200; state: 8`, then PASS. The existing cases cover
scan/connect, supported UART profiles, notification and indication reception,
write credits and timeout, authentication refusal, overflow, disconnect, cleanup
uncertainty, and ten close/reopen cycles. The target build validates Xtensa ELF
identity and the existing allowed import/export contract. Build receipts and
logs record the exact artifact hash; these are host/build evidence, not physical
qualification.
